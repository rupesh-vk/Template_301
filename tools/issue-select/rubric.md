# Rubric: is this a good first issue?

## Checks

Use the bundle capture date for eval recency and today's date for live recency. Evaluate the issue body, full supplied thread, and repo facts together. Labels and star counts never override a failed required check.

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Human maintenance | Repo-facts last 5 default-branch commits, author names and merged PR authors; dated owner/member/collaborator comments in the issue thread; maintainer first-response sample. In live mode use the corresponding commit history and issue threads. | At least one human-authored default-branch commit or merge of a human-authored PR within 90 days, OR at least one owner/member/collaborator reply in the candidate thread within 90 days. Automated dependency updates alone do not pass. A short historical response latency without a recent dated interaction does not prove current activity. | required |
| Repository continuity | Repo-facts archived flag, latest release date and last push date; in live mode repository metadata, releases and commit history. | Repository is not archived and has either a release within 365 days or a push within 90 days. No published release is acceptable when recent development meets the push threshold. Stars are context, not a minimum requirement. | required |
| Bounded contribution | Issue body, labels, opener association, full comment thread, and history of abandoned PRs. | Work addresses one identifiable bug, documentation/test correction, or small feature. Reject pure usage/support questions, umbrella/tracking work with independent subprojects, explicitly unresolved design disputes, stated core parser/architecture changes, or repeated abandoned attempts showing hidden complexity. A terse report, missing reproduction steps, or lack of an explicit maintainer approval is not by itself a failure when the requested change is concrete and no contrary scope evidence appears. | required |
| Available work | Issue state, assignees, linked PR states, and the entire comment thread including informal PR references and work claims. | Issue is open, with no assignee, no open implementation PR, and no unwithdrawn explicit work claim or reported implementation PR in the thread. Empty sidebar fields do not override a claim in comments. A closed unmerged PR alone is not an active claim. Apply the live scope's classroom house rule to classmates' claim comments; eval snapshots have no classroom exception. | required |
| Compatible contribution policy | Bundle contribution-policy summary; in live mode CONTRIBUTING.md, linked AI policy files, AGENTS.md and contribution templates. | Policy permits AI-assisted contributions or states no restriction. Disclosure, understanding, testing and human-review conditions pass and must be followed. An explicit prohibition covering this AI-assisted workflow fails. A ban on fully AI-generated submissions with an explicit allowance for assistive use passes under that allowance. Missing evidence about whether a policy was checked is unclear; an explicit statement that the checked policy is silent passes. | required |
| Easy verification | Issue body and comments: example input, observed and expected behavior, named file/function, or concrete acceptance criteria. | At least one concrete input/output example, named correction site, or testable acceptance criterion is supplied. This only ranks accepted issues; its absence never rejects an otherwise bounded issue. | preferred |

## Verdict rule

Accept if and only if every required check is pass. Any required fail or unclear means reject. Preferred checks never change the verdict; their passes help rank accepted candidates together with the live fit profile. Mark unclear only when evidence needed by the stated condition is genuinely absent. Give one deciding evidence fact for each grade.
