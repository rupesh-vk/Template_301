# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The repro report's environment record, read against the versions, platform, and project revision the issue names (see `## Environment` in `references/evidence-guide.md`). | The record names all three of: the operating system, the language/runtime version, and the project version or commit the reproduction ran against; and each either matches what the issue targets or the report states the difference. Missing any one of the three fails. A difference from the issue's target that the report never mentions fails, because a reader cannot tell whether the environment or the bug produced the result. | required |
| Steps re-runnable by a stranger | The reproduction steps in the repro report, read as an ordered sequence from a stated starting state to the trigger, together with every input those steps consume (files, commands, data, config) and any setup the report says it relied on. | A reader who has the recorded environment and no other context could execute the steps in order and reach the trigger: the starting state is stated, every input the run consumes is supplied or linked, and no step depends on a fact the package never states. A step that says to set the project up without naming the doc or command that does it, or that consumes a fixture the package never supplies, fails. | required |
| Behavior shown matches the issue | The artifacts (output excerpts, logs, tracebacks, screenshots) read against the behavior the issue's description states, not against the report's own summary of them. | The artifact exhibits the behavior the issue describes — the same failing operation on the same surface, with the same observable symptom. An artifact showing an adjacent fault (a different error, an install or setup failure, a symptom of a mis-built environment) fails. An artifact showing a failure that the package never ties to the issue's stated behavior grades unclear, not pass. | required |
| Outcome stated honestly | The assertions made in the claim comment and the repro report, each read against what the package's artifacts actually show. | Every assertion the words make is backed by something in the package, and the stated outcome matches the strength of that evidence. A report that states it could not reproduce, records what it ran, and shows the result it got instead, passes — that is an honest outcome, not a failed one. A report asserting the bug reproduced while its artifact shows an adjacent fault fails. A report asserting a cause or a fix the evidence does not show fails. | required |
| Repo conventions and disclosure | The posted or drafted comments read against the repo-facts block and the repo's own stated rules: its contribution policy, its issue or report templates, and any requirement to disclose AI assistance (see `## Comms` in `references/evidence-guide.md`). | Every stated requirement that applies to these comments is met in the text of the comments themselves. If the repo's policy requires disclosing AI assistance and the package was AI-assisted, a disclosure is present in the posted text. If the repo supplies a template for this kind of comment, its required fields are filled. A requirement the repo states and the comments do not meet fails. A requirement the repo is silent on cannot fail here. | required |
| Claim promises only investigation | The claim comment read against the issue thread. | The claim names this issue's own specifics (not boilerplate that would fit any issue) and commits only to investigating and reporting back. It promises no fix, no design, and no delivery date. | preferred |

## Verdict rule

Accept if every `required` check grades pass. Any single `required` check grading fail makes the verdict reject — a required fail holds the package regardless of how the others went.

An `unclear` grade on a required check counts as a fail. The package is addressed to a maintainer who has only what is in front of them; if this grader has to guess what the evidence shows, that maintainer would have to guess too, and the package is not ready. Writing the missing thing down is cheap, and that is the revision the reject is asking for.

`preferred` checks never change the verdict. They are reported in the output so the author can act on them before posting, and a package may be accepted with every preferred check failing.

The output quotes the evidence for the deciding check: on a reject, the first required check that failed and what the package showed instead; on an accept, the required check whose evidence was thinnest.
