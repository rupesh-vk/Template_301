# Evidence guide: where proof lives in a reproduction package

## Environment

**Where it lives.** In an eval package: the repro report's environment record, usually a fenced block or short list near the top of the report, under a heading such as Environment or Setup; the issue context section states the target that record has to be read against (the version, platform, or revision the issue says it affects); the repo-facts block states the project's supported versions when the issue does not. In live mode: the environment record in my drafted repro comment, read against the issue body's own version statement on the GitHub thread, and against the project's README or installation doc for what the project considers a supported setup.

**What good looks like.** The record names the operating system, the language or runtime version, and the project version or commit, and each is a value someone could type back — `Python 3.11.6`, `commit a4f91c2`, `macOS 14.5` — not a category like "latest" or "my machine". Where one of those differs from what the issue targets, the report says so in a sentence rather than leaving the reader to notice. A record is sufficient when a reader could rebuild the same machine state from it, and would know without asking whether their differing result meant a different bug or a different box.

## Steps

**Where it lives.** In an eval package: the numbered or bulleted reproduction steps in the repro report, plus whatever the report supplies alongside them — the input file or fixture, the exact command, the config values, any seed data — and any setup the report says it followed, which usually points at a doc named in the repo-facts block. In live mode: the steps in my drafted repro comment, read against the repo's own setup documentation (README, CONTRIBUTING, docs/) for whatever the steps delegate to it.

**What good looks like.** The steps begin from a stated starting state — a fresh clone at a named revision, a named install command, a named working directory — and end at the trigger, with nothing in between that depends on a fact the package never states. Every input the run consumes is in the package or linked from it: if a step feeds a file in, the file's contents are shown or linked; if a step runs a command, the command is written out and not paraphrased. A step that delegates to the project's own setup names the doc it delegates to. The test is whether a stranger with the recorded environment could execute the sequence without stopping to ask me a question; if there is a question they would have to ask, that is the step to fix.

## Behavior shown

**Where it lives.** In an eval package: the artifacts in the repro report — output excerpts, log lines, tracebacks, screenshots, test output — read against the behavior the *issue's description* states, not against the report's own summary of what it believes it showed. The issue context section carries the stated behavior; the artifact carries what actually happened. In live mode: the output pasted in my draft comment, read against the issue body on the thread.

**What good looks like.** The artifact shows the same failing operation on the same surface, with the same observable symptom the issue names: the issue's error text appears in my output, or the issue's wrong value appears where it said it would, or the issue's named test fails with the issue's named assertion. An artifact shows an *adjacent* fault when it fails for a reason the issue did not describe — an install error, a missing dependency, a different exception from a different call, a symptom traceable to the environment being built wrong rather than to the bug. Adjacency is the common and dangerous case, because such a report looks complete and confident while proving nothing about the issue. Where an artifact shows some failure but the package never ties it to the issue's stated behavior, that is not proof and not disproof: it is a gap, and I grade it unclear.

## Honesty

**Where it lives.** At the join between two parts of the package: the assertions, which live in the claim comment's sentences and the repro report's prose and summary lines, and their backing, which lives in the artifacts and the environment record. The check is performed by reading each assertion and asking which artifact supports it. In live mode: the same join, between the sentences in my draft comment and the output I pasted under them.

**What good looks like.** Every assertion is traceable to something in the package, and the strength of the words matches the strength of what is shown. A report that reproduced the bug says so and shows the artifact that proves it. A report that could not reproduce says *that*, records exactly what it ran and in what environment, and shows the result it got instead — that is a complete and passing package, because a faithful negative result is real information for the maintainer and is often the most useful thing an issue thread receives. The failures look like this: words that assert the bug reproduced over an artifact showing an adjacent fault; words that name a cause ("the regex is anchored wrong") when the artifact only shows a symptom; words that promise a fix the package has not tested; hedging that hides which of two outcomes actually occurred. The question to ask of each sentence is whether I could point at the line in the package that earns it.

## Comms

**Where it lives.** Where the words meet the repo's own stated rules. The words: the claim comment and the repro comment, as drafted or as posted. The rules: the repo-facts block in an eval package, and in live mode the repo's `CONTRIBUTING.md`, its `README`, its `.github/` issue and PR templates, any `AGENTS.md` or AI-use policy file, and the issue thread itself for what maintainers have asked of contributors there. The claim comment is additionally read against the issue body, for whether it names this issue or any issue.

**What good looks like.** Every requirement the repo *states* and that applies to these comments is satisfied in the text of the comments themselves — not in my intentions, and not elsewhere in the package. The sharpest case is AI-assistance disclosure: where the repo's policy requires contributors to disclose AI assistance, an AI-assisted package whose comments carry no disclosure fails, however good its evidence is, and no amount of thorough reproduction buys that back. Where the repo supplies a template for this kind of comment, its required fields are filled rather than deleted. A repo that is silent on a requirement cannot fail on it; silence is permission here, and I do not invent rules the repo never wrote. Separately, specific-and-honest means a comment that could only have been written about *this* issue — it names the function, the input, the version, the thing I actually observed — as against boilerplate that would read identically under any issue in the tracker.
